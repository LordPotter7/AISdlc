01 · Is this for you?

Use it when the record matters

The framework adds gates and evidence to every change. That's worth it when someone will later ask "how do we know this works?", and overkill for a weekend script.

Good fit

  • A team lets Claude write production code and needs to show it was checked
  • Changes touch security, data, model behaviour, or public interfaces
  • You want traceability from requirement → Task → evidence → acceptance
  • Compliance asks for evidence (NIST AI RMF, ISO/IEC 42001, SSDF export)
  • An existing codebase you want to change without regressions

Probably skip it

  • Throwaway prototypes and spikes
  • Solo scripts nobody else will rely on
  • You need release or deployment automation: both stay outside this lifecycle
  • You need signed, third-party-verifiable provenance: evidence is hashed, not signed
💡Installing changes nothing until you opt a repository in. The guard hooks stay silent in every repository without a .ai-sdlc/ folder, so the plugin is safe to install once and use where you choose.
02 · Install

Three steps, nothing on your PATH

The runner is a Python script inside the plugin folder, run with the python3 you already have. There's no package to install and nothing else to upgrade.

1

Add the marketplace

In Claude Code, add this repository from GitHub, or from a local checkout.

/plugin marketplace add <owner>/<repo>
2

Install the plugin

Use the marketplace name the previous step reported. /plugin marketplace list shows it.

/plugin install aisdlc@aisdlc-local
3

Opt a repository in

Open your project in Claude Code, scaffold it, then check readiness.

/aisdlc:init
/aisdlc:doctor
Claude Codewith the plugin installed
Python 3.12+on PATH as python3, python or py
Gitevery evidence manifest is pinned to a commit
⌨️About ai-sdlc in this guide. Most work uses the /aisdlc:* slash commands. Where a raw runner command appears, ai-sdlc is shorthand for python3 "${CLAUDE_PLUGIN_ROOT}/scripts/lifecycle.py". Nothing named ai-sdlc is on your PATH. Inside Claude Code you rarely type these yourself; the slash commands run them for you. 03 · Core concepts

Twelve words you'll see everywhere

Work is organised as a strict three-level hierarchy. There are no subtasks, by design.

Intent I001 · one outcome you want, e.g. "Add a health endpoint"
Build Phase I001-P00 · walking skeleton, then I001-P01, P02…
Task I001-P00-T001 · one verifiable unit of work

Each Intent moves through seven stages and five human gates. It is planned into Build Phases, and each phase holds Tasks. Every Task traces to exactly one approved requirement, finding, or decision, and proves itself with captured evidence.

Identifiers are allocated by the runner, never chosen by hand, and are never reused, even after a failure.

Gate G1–G5
A decision only a human records. G3 lets any Task run. G4 accepts the walking skeleton. G5 is final acceptance.
Runner
The deterministic script that owns IDs, state, gates, locks, evidence and the audit log. It lives in the plugin folder, outside your repo.
Walking skeleton (P00)
The thinnest end-to-end slice that proves the approach. Later phases run only after you approve it at G4.
Acceptance criterion
A testable condition with exactly one verification class: D, S, J or N (see Verification).
Visible vs held-out
Visible checks may be written by the implementer. Held-out checks may not: they come from the spec, a reviewer, or a human.
Evidence manifest
What verify-task writes: commands, exit codes, SHA-256 hashes and the Git commit, with secrets masked first.
Model family
A model ID reduced to vendor and name: claude-opus-5-5 → claude-opus. Opus and Sonnet count as different families.
Pre-gate review
A red-team review of the spec (before G2) or plan (before G3), from a fresh context. The runner refuses G3 without one.
Convergence
The final check before G5: evidence, spec pins, traceability and held-out coverage, all on a clean, committed tree.
Compact vs full
Compact is for small, deterministic changes; G2 and G3 can be approved together. Full is for everything else, and always for model behaviour.
Conformance gap
Visible checks pass but held-out checks fail: the code fits its tests, not the requirement. Fix the code, never the held-out test.
Lesson
A severe finding promoted at close into durable enforcement (a regression eval, policy or checklist) that later Intents inherit.
04 · Who decides

Three actors, and only one keeps score

Anything a conversation can't be trusted with belongs to code outside the conversation. Every step in this guide is labelled with who acts.

YOU

Approve

  • Approve gates G1–G5 explicitly
  • Say what "done" means; accept the result
  • Resolve escalations when a Task is blocked
  • Write or approve held-out checks
CLAUDE

Draft and build

  • Frame briefs, write specs and plans
  • Implement Tasks and visible tests
  • Review from a fresh context (verifier, red-team)
  • Never approves a gate, or infers your approval
  • Never edits runner-owned files or held-out checks
RUNNER

Keep the record

  • Allocates permanent identifiers
  • Owns state, gates, locks and retry limits
  • Captures evidence pinned to a commit
  • Generates traceability and the audit log
Rule of thumb: if the runner didn't record it, it didn't happen. A refusal from the runner is the design working. It names what's missing.
05 · Quickstart

Your first change, end to end

The complete sequence for one Intent, with every gate. YOU steps are decisions only you can make. Claude stops and waits for each one. Tick steps off as you go; your progress is saved in this browser.

0 of 13 done
  1. 1

    Set up the repository

    CLAUDE

    Scaffolds .ai-sdlc/, AGENTS.md and the gitignore rules, then reports readiness. Fix every fail first. Once per repository.

    Claude Code
    /aisdlc:init
    Claude Code
    /aisdlc:doctor
  2. 2

    Fill in the project context

    YOU

    Edit .ai-sdlc/project-context.md: your conventions and your real verification commands (tests, lint, type check). They become Class D criteria for every Task, so an empty stub weakens everything. This is the highest-value five minutes of setup. Claude can draft it from your repo for you to check.

  3. 3

    Start an Intent

    CLAUDEstops at G1

    Claude asks what should change and for whom, agrees the mode with you (compact or full), registers the Intent (the runner assigns I001), drafts the brief and sets trigger flags such as contains_model_behavior.

    Claude Code
    /aisdlc:start "Add a health endpoint"
  4. 4

    Approve the brief

    YOUG1

    Read the brief and its trigger flags. Want a summary first? /aisdlc:gate-packet I001 G1 builds one. Replace you with your name. The approver is a plain argument, not --approver.

    Claude Code
    /aisdlc:gate I001 G1 you
  5. 5

    Specify

    CLAUDEstops at G2

    Writes testable requirements and acceptance criteria, each with one class (D/S/J/N), runs the spec linter, and has the aisdlc-red-team agent review the spec from a fresh context.

    Claude Code
    /aisdlc:specify I001
  6. 6

    Approve the specification

    YOUG2

    Approving G2 freezes the spec. Changing it later means reopening G2, which invalidates evidence pinned to it.

    Claude Code
    /aisdlc:gate I001 G2 you
  7. 7

    Plan

    CLAUDEstops at G3

    Records architecture decisions, then breaks the work into Build Phases (P00 walking skeleton first) and Tasks. Each Task declares its paths, resources, criteria and commands. A red-team review of the plan follows; the runner refuses G3 without it.

    Claude Code
    /aisdlc:plan I001
  8. 8

    Approve the plan

    YOUG3

    G3 is what allows any Task to run. Check the Task list, each Task's traceability, and its held-out checks.

    Claude Code
    /aisdlc:gate I001 G3 you
  9. 8

    Approve spec and plan together

    YOUG2-G3

    Compact mode only: one combined review of the spec and the plan. It's accepted only while the Intent is still specified and neither gate has been decided.

    Claude Code
    /aisdlc:gate I001 G2-G3 you
  10. 9

    Build the walking skeleton

    CLAUDERUNNER

    For each ready Task, Claude implements inside the declared paths. The runner runs verify-task, capturing commit-pinned evidence for the visible and held-out checks. Then aisdlc-verifier reviews it from a fresh context and the review is registered. Two retries are allowed; a third failure blocks the Task for you to resolve.

    Claude Code
    /aisdlc:run I001
  11. 10

    Accept the walking skeleton

    YOUG4

    Required even when the Intent has only P00: convergence refuses without G4. If there are later phases, run /aisdlc:run I001 again after approving to build them.

    Claude Code
    /aisdlc:gate I001 G4 you
  12. 11

    Verify

    CLAUDERUNNERstops at G5

    Regenerates traceability and runs convergence: evidence integrity, spec pins, held-out coverage, inherited suites, open findings, and a clean committed tree. Any failure is named with what would satisfy it.

    Claude Code
    /aisdlc:verify I001
  13. 12

    Give final acceptance

    YOUG5

    The precondition for close.

    Claude Code
    /aisdlc:gate I001 G5 you
  14. 13

    Close

    CLAUDERUNNER

    Writes the completion result, including what the plan didn't anticipate, and promotes severe findings to lessons that future Intents inherit. Nothing is tagged, published or deployed.

    Claude Code
    /aisdlc:close I001
🧭Lost at any point? /aisdlc:status I001 shows the Intent's state, its gates, ready Tasks, and the legal next actions.
06 · Daily workflow

What you actually type on a normal day

After setup, nearly every session follows the same loop. You don't need to remember the lifecycle: the runner tells you what's next.

1 · ASK

Where are we?

/aisdlc:status lists every Intent; /aisdlc:status I001 lists its legal next actions.

2 · DO

Run what it names

Usually /aisdlc:specify, /aisdlc:plan, /aisdlc:run or /aisdlc:verify.

3 · DECIDE

Approve when asked

Read the packet (/aisdlc:gate-packet), then /aisdlc:gate I001 Gx you.

4 · REPEAT

Until close

Refused? Read the reason; it names the missing approval or artifact.

Where your records live

One folder per Intent, committed with your code. Files marked runner are written only by the runner. Never edit them.

delivery/intents/I001-add-health-endpoint/
  00-intent/intent.yaml
  01-brief/brief.md
  02-specification/requirements.yaml
  03-planning/plan.md
  04-build/I001-P00/
    phase.yaml
    tasks/I001-P00-T001/
      task.yaml
      evidence/          # runner
      review.yaml        # runner
  05-verification/
  06-close/
  traceability.json    # runner

Habits that keep it smooth

  • Commit before verifying. Evidence is pinned to a commit, and convergence needs a clean tree.
  • Never commit .ai-sdlc/runtime/. init gitignores it. Committing it makes convergence impossible.
  • Held-out failure? Fix the code. It isn't flaky; it's the most useful signal you'll get.
  • State looks wrong? Don't hand-edit JSON. Run ai-sdlc repair-state --confirm.
  • Need to work unmanaged for a while? Set AISDLC_HOOKS=off to pause the guards.
07 · Onboarding paths

Pick your starting point

Five entry points, each aiming to reach a working, verified state quickly.

⏱ quickest path

Path A · a brand-new repository

Nothing to discover yet. Scaffold, check, describe your conventions, ship one small change.

  1. Install, then /aisdlc:init and /aisdlc:doctor
  2. Fill in .ai-sdlc/project-context.md
  3. Run one small compact Intent end to end: the Quickstart
Claude Code
/aisdlc:init compact
Claude Code
/aisdlc:start "Add a health endpoint"
⏱ about 30 minutes to orient

Path B · an existing codebase

"State what it should do, then prove it" turns into fiction on a legacy system. First record what it is, then pin what it does.

  1. /aisdlc:init and /aisdlc:doctor
  2. Build an understanding from one source, code or docs, never both. Every claim carries a [path:lines] anchor
  3. Validate its anchors and pin it to a commit with understand record
  4. Copy the checks you accept into a probes file yourself. There's no promote command, by design
  5. Capture a baseline, then write criteria like "no worse than BASELINE-001"
Claude Code
/aisdlc:understand repo
runner
ai-sdlc understand record
Claude Code
/aisdlc:baseline probes.yaml
runner
ai-sdlc baseline compare BASELINE-001
⏱ about 20 minutes of reading

Path C · a new teammate

The repository already uses the lifecycle. Read three files, then shadow one change.

  1. AGENTS.md: short; it lists what the runner will refuse
  2. .ai-sdlc/constitution.md: about one page of non-negotiable rules
  3. This guide's Quickstart, then shadow one compact Intent
  4. On brownfield repos, also .ai-sdlc/project-understanding.md
🚫The three classic early mistakes: hand-editing .ai-sdlc/runtime/ to "fix" a state; retrying a held-out failure as if it were flaky; committing .ai-sdlc/runtime/.
Claude Code
/aisdlc:status
⏱ about 5 minutes

Path D · a non-Claude agent

Any agent may drive the lifecycle; none may decide it. The runner is plain Python with no dependencies.

  1. Find the installed plugin folder once
  2. Run the runner with any stock Python 3.12+ (python3, python or py)
  3. Follow AGENTS.md in the repository root
shell
python3 <plugin-dir>/scripts/lifecycle.py --help
shell
python3 <plugin-dir>/scripts/lifecycle.py status
⏱ incremental

Path E · organisation scale

Several teams, long initiatives, or compliance requirements.

  1. Group Intents into a Program, with ordering and a roll-up
  2. Declare shared resources so contention is visible: intent-resources, coapprove-resource
  3. Pick a stricter pipeline profile where needed: tighten freely, loosen only by recorded waiver
  4. Export evidence for NIST AI RMF, ISO/IEC 42001 and SSDF

/aisdlc:program new --title "Checkout v2" --owner you
runner

08 · Lifecycle stages

Seven stages, five gates, in detail

Pick a stage to see what happens, which folder it fills, and what the runner refuses there.

Stage 0 · register

Give the change a permanent identity

The runner registers the Intent and allocates I001. Identifiers are never reused or renumbered, even after failure. Registration records the mode (compact or full) and whether discovery is needed.

00-intent/intent.yamlaudit event

/aisdlc:start "Add a health endpoint"

The runner refuses

  • Choosing or reusing an identifier by hand
  • Compact mode for an Intent with model behaviour

Next

Framing happens in the same /aisdlc:start run.

Stage 1 · frame · gate G1

Agree on the outcome

Claude drafts a brief: the outcome, who it's for, how you'll know it worked, and trigger flags (retrieval_grounded, contains_model_behavior, multi_tenant, has_side_effect). The flags decide which standing regression suites are inherited.

01-brief/brief.md
Claude Code
/aisdlc:gate I001 G1 you

The runner refuses

  • Specifying before G1 is approved
  • Claude approving the gate itself

G1 authorizes

The framed brief and its trigger flags.

Stage 2 · specify · gate G2

Make "done" testable

Requirements written as single obligations, with acceptance criteria that each carry exactly one class. Contracts go under contracts/. A threat model is added when the flags require it. A red-team pre-gate review checks the spec from a fresh context.

02-specification/requirements.yamlcontracts/threat model
Claude Code
/aisdlc:specify I001

The runner refuses

  • A criterion with zero or two classes
  • Advancing past spec-lint errors (specification.fail_on)
  • Editing an approved spec without reopening G2

G2 authorizes

The specification, which approving freezes. In compact mode it's combined with G3 as G2-G3.

Stage 3 · plan · gate G3

Decide the architecture, then the tasks

Structural choices are recorded first as decisions. Then the Build Phases are ordered by dependency, with P00 as the walking skeleton. Every Task traces to exactly one requirement, finding or decision, and declares its paths, shared resources, criteria and commands.

03-planning/decisionsphase.yamltask.yaml
Claude Code
/aisdlc:plan I001

The runner refuses

  • G3 without a pre-gate review of the plan
  • A Task that traces to nothing
  • Running any Task before G3

G3 authorizes

The plan, and with it the execution of any Task.

Stage 4 · build · gate G4

Implement under locks, prove with evidence

The runner picks the dependency- and lock-safe ready batch. Each Task is implemented inside its declared paths, verified by the runner, and reviewed by a verifier from a different model family. G4 accepts the P00 walking skeleton and releases the later phases.

Claude Code
/aisdlc:run I001

The runner refuses

  • Marking a Task complete without captured evidence
  • A review from the implementer's model family
  • Phases after P00 before G4
  • A fourth attempt after two retries

G4 authorizes

Release of the phases after P00. Convergence also requires it.

Stage 5 · converge · gate G5

Check everything together

Evidence integrity and commit pins, spec conformance (visible vs held-out), held-out coverage, bidirectional traceability, inherited suites, open findings, and phase exits, all on a clean committed tree.

  • Converging with an unresolved conformance gap
  • Uncommitted source changes
  • Converging without G4

Final acceptance, the precondition for close.

Stage 6 · close

Record the result, keep the lessons

The completion result notes what the plan didn't anticipate. Severe findings become lessons with a firing target: a regression eval (strongest), a policy, a checklist item, or a context heuristic (weakest).

  • Closing before G5
  • A Critical or High finding without a blocking target

Out of scope

Release and deployment. Nothing is tagged, published or deployed.

09 · Verification

How a Task proves it is done

Every acceptance criterion has exactly one class. Prefer D: reach for S, J or N only when a command genuinely can't settle the question, because each one carries a dataset, a pin and a recurring cost.

D

Deterministic

A command exits zero or non-zero. Tests, linters, type checks, migrations.

pytest -q tests/test_health.py
S

Statistical

A rate over a versioned dataset, with threshold and tolerance declared before any run. At least 3 runs.

e.g. pass rate ≥ your threshold
J

Judged

A pinned judge with a binary rubric and exemplars, from a different family than the generator. Agreement floor 0.85.

2+ exemplars · 5% human audit
N

Adversarial

An attack suite where the only passing result is zero successes: injection, jailbreaks, tenant isolation.

aisdlc-red-team
01 · DECLARE

task.yaml

Paths, resources, criteria, visible and held-out commands.

02 · CAPTURE

verify-task

Runs both suites against one commit; masks secrets, then hashes.

03 · PIN

manifest

Commands, exit codes, SHA-256, sandbox posture, Git commit.

04 · REVIEW

review-task

Fresh context, different model family, checked against the manifest.

05 · MERGE

merge-ready

Same commit, not stale, no conflict markers.

Visible checks pass, held-out checks fail? That's a specification-conformance gap: the code satisfies the tests it was given, not the requirement. Fix the implementation. Never the held-out test. It isn't a flaky test, so don't retry it as one.
🧪Reviewer independence in practice. The bundled aisdlc-verifier agent runs on Opus. If your implementing session also runs on an Opus model, both reduce to claude-opus, so the runner rejects the review. Set review.reviewer_model in .ai-sdlc/config.yaml to a model from another family. A review with no reviewer_model at all is also rejected: the runner fails closed.

12 · Troubleshooting

When the runner says no

A refusal is the design working: it names what's missing. Start with /aisdlc:status I001, then find the message below.

Gate 3 must be approved before executing Tasks
The plan isn't approved yet. Review it and run /aisdlc:gate I001 G3 you, or G2-G3 in compact mode.
Gate 4 must approve the walking skeleton
Phases after P00 wait for G4. Review the P00 results and run /aisdlc:gate I001 G4 you, then /aisdlc:run I001 again.
Gate 4 is not approved (at verify)
Convergence needs G4 even when the Intent has only P00. Approve G4, then rerun /aisdlc:verify I001.
illegal transition / gate requires another state
Something was attempted out of order. For example, G2-G3 is only accepted while the Intent is specified and neither gate is decided. /aisdlc:status shows the current state and the legal next actions.
Pre-gate review missing
G3 needs a fresh-context red-team review of the plan, registered with ai-sdlc pre-gate-review I001 G3 --from <file>. /aisdlc:plan asks for it. Rerun that step if it was skipped.
may not approve
The approver isn't in that gate's list. Route it to a declared approver, or amend gates.approvers in .ai-sdlc/config.yaml.
Specification-conformance gap
The visible suite passes; the held-out suite fails. Fix the implementation, never the held-out test. It's the most informative signal the framework produces.
declares no held-out instrument
A behavioural Task has no independent check. Add holdout_commands, or record a holdout_waiver with a reason and an approver.
reviewer_model missing or same family
Independence can't be established. Use a reviewer from another family (Opus vs Sonnet counts) and set review.reviewer_model.
Task is blocked
The retry limit was exceeded and an escalation package was written. Resolve it, then continue the Task's worktree with ai-sdlc worktree resume, or abandon the Task with ai-sdlc fail-task <task> --reason "…".
tracked source changes are not committed
Convergence needs a clean tree. Commit your intended changes, recapture evidence if the commit moved, then verify again.
commits behind / pin mismatch
The verified base is stale, or a mapped requirement changed. Rebase and re-verify against the approved revision.
Runner state looks corrupt
Don't edit JSON. Run ai-sdlc repair-state --confirm. It validates the audit sequence, keeps the unreadable file as state.corrupt-*.json, and rebuilds.
Guards inactive / no python3 >= 3.12
The hooks need a POSIX shell and Python 3.12+ on PATH. On Windows, both usually come with Git for Windows and a normal Python install. Re-run /aisdlc:doctor.

Know before you rely on it

⚙️Verification runs code. /aisdlc:run and /aisdlc:verify execute the repository's declared commands. Treat them like npm test on untrusted code.
🛡️Guards fail open. Without a POSIX shell or Python 3.12+, the hooks warn on stderr and allow the action. Read a runner: fail line from doctor as "guards are off".
⌨️Shell writes aren't guarded. The guard watches Claude's file-editing tools. A Bash command that writes .ai-sdlc/runtime/ isn't intercepted, so review such commands yourself.
🔏Evidence is hashed, not signed. It stops agents from grading their own work. It doesn't prove anything to a third party who doesn't trust your machine.
